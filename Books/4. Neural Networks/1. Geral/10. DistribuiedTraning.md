# Distributed Training

For the training in ML world, we find some troubles, like:

- Problem 1: the model is too big to fit in a single GPU's memory. A typical GPU has between 24GB and 80GB. A model with billions of parameters, plus gradients, plus optimizer states (Adam keeps two extra moments per parameter), simply doesn't fit. You need to split the model itself across multiple GPUs.

- Problem 2: training is too slow on a single GPU. Even if the model fit, processing all the training data sequentially would take weeks or months. You want multiple GPUs processing data in parallel to cut total training time.

---

# 1. Data Parallel (DP / DDP)

## What it solves
Problem 2 (speed) — **not** Problem 1 (model size).

## How it works
The **full model is copied** to every GPU (every rank). Each GPU has an identical, complete copy of all parameters.

```
GPU 0: full model copy
GPU 1: full model copy
GPU 2: full model copy
GPU 3: full model copy
```

Each GPU processes a **different slice of the batch**:

```
GPU 0 → processes batch[0:32]
GPU 1 → processes batch[32:64]
GPU 2 → processes batch[64:96]
GPU 3 → processes batch[96:128]
```

Each GPU runs forward + backward independently on its own slice, producing its own gradients. Then:

```
all-reduce: gradients from all GPUs are averaged and synced across all GPUs
```

After that, every GPU has the same averaged gradient, and does the same optimizer step — so all copies of the model stay identical.

## The catch
Every GPU still needs to hold the **entire model + entire gradients + entire optimizer states** in memory. DP does nothing to reduce memory per GPU — it only splits the **data**, not the **model**.

So DP solves Problem 2 (speed via parallel data processing), but does nothing for Problem 1 (a model too big for one GPU).


---

# 2. FSDP (Fully Sharded Data Parallel)

## What it solves
Both Problem 1 (model size) **and** Problem 2 (speed).

## How it works
Instead of every GPU holding a full copy, the model's parameters (and gradients, and optimizer states) are **split (sharded)** across GPUs. Each GPU only holds a **fraction** of everything.

```
GPU 0: 1/4 of the parameters
GPU 1: 1/4 of the parameters
GPU 2: 1/4 of the parameters
GPU 3: 1/4 of the parameters
```

No GPU ever holds the full model at rest. This is what solves Problem 1 — you can train models that wouldn't fit on a single GPU, because each GPU only needs to store its shard.

## What happens during forward/backward
To actually compute anything, the full parameters of a given layer/unit need to be reconstructed temporarily:

```
1. all-gather: GPUs exchange shards to reconstruct the full layer, on every GPU
2. compute: forward (or backward) runs normally with the full layer in memory
3. re-shard: once done, each GPU discards everything except its own shard again
```

This repeats **unit by unit** (see `auto wrap policy` — it defines what counts as one of these units), so the full model is never fully materialized on every GPU at once — only one unit at a time.

## Same data split as DP
FSDP still splits the **batch** across GPUs like DP does (each GPU processes a different slice of data). The difference is purely about **how the model itself is stored** — sharded (FSDP) vs fully replicated (DP).

## Trade-off vs DP
- **Memory:** much lower per GPU (this is the whole point).
- **Communication:** higher — DP only does one all-reduce (gradients) per step; FSDP does all-gather + re-shard for every unit, on every forward **and** every backward.
- **Speed:** with good overlap between communication and computation (prefetching the next unit while computing the current one), FSDP throughput can get close to DP, despite the extra communication.

---

# Summary

| | Data Parallel (DDP) | FSDP |
|---|---|---|
| Model copy per GPU | Full copy | Sharded (fraction only) |
| Solves "model too big" | No | Yes |
| Solves "training too slow" | Yes | Yes |
| Communication per step | 1 all-reduce (gradients) | all-gather + re-shard per unit, forward and backward |
| Memory per GPU | High (full model + grads + optimizer states) | Low (only its shard) |
| When to use | Model fits comfortably on 1 GPU, just want more speed | Model doesn't fit on 1 GPU (or barely fits) |
