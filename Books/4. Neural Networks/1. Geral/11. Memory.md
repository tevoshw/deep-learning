# Floating Point Representation & Memory Optimization in Deep Learning

A reference on numerical representation and memory-saving techniques used in large-scale model training (FSDP, activation checkpointing, mixed precision).

---

## 1. Bits vs. Bytes

- **Bit**: the fundamental unit, `0` or `1` — an on/off switch.
- **Byte**: a group of 8 bits. It's the basic addressable unit in memory.

**The connection**: when we talk about precision (e.g. `float32`), we're talking about **4 bytes (32 bits)** to represent a single number. This directly determines how much VRAM a tensor consumes — precision isn't just about accuracy, it's a memory cost decision.

---

## 2. Binary Normalization

To store a decimal number (e.g. `0.034`) in a fixed number of bits, the computer needs a standardized format. The normalization process:

1. Convert the number to binary.
2. Shift the decimal point so there's exactly one `1` before it (`1.xxxx...`).
3. The number of positions the point shifted defines the **exponent**.

This is the same idea behind scientific notation (`1.23 × 10^n`), just in base 2 instead of base 10.

---

## 3. Structure of a Floating-Point Number (Sign, Exponent, Mantissa)

Every floating-point number (like `float32`) is split into three fixed "buckets":

| Field | Size (float32) | Purpose |
|---|---|---|
| **Sign** | 1 bit | `0` = positive, `1` = negative |
| **Exponent** | 8 bits | Defines the scale (position of the decimal point). Uses a **bias (127)** so negative exponents can be stored without a dedicated sign bit |
| **Mantissa** | 23 bits | Defines precision — the fractional part (`.xxxx...`). The leading `1.` is implicit, so we get "free precision" without spending a bit on it |

```
float32 layout:
[S][EEEEEEEE][MMMMMMMMMMMMMMMMMMMMMMM]
 1     8                23        = 32 bits total
```

Different formats trade mantissa bits (precision) for exponent bits (dynamic range) — this trade-off is exactly what separates `fp16` from `bf16` (see below).

---

## 4. Mixed Precision Training

Mixed precision trains using two numerical "worlds" at once:

- **Fast computation (forward/backward)**: uses `bfloat16` — 7 mantissa bits, 8 exponent bits (same exponent range as `float32`). It's fast, uses half the memory of `float32`, and rarely overflows because it inherits `float32`'s dynamic range.
- **Weight updates (master weights)**: a copy of the weights is kept in `float32`. This acts as a safety net, ensuring tiny gradient updates aren't silently rounded away to zero by `bfloat16`'s lower mantissa precision.

### `bf16` vs `fp16`

| | `float16` | `bfloat16` |
|---|---|---|
| Exponent bits | 5 | 8 (same as fp32) |
| Mantissa bits | 10 | 7 |
| Dynamic range | Smaller — overflow/underflow more likely | Same as fp32 — rarely overflows |
| Precision | Higher | Lower |
| Needs loss scaling? | Usually yes | Usually no |

`bf16` is generally preferred for LLM training because it avoids the operational overhead of loss scaling — a technique required to compensate for `fp16`'s limited dynamic range.

**Hardware note**: `bf16` is only natively accelerated (via Tensor Cores) on NVIDIA Ampere or newer (A100, H100, RTX 30xx+). Older GPUs (V100, T4, RTX 20xx) don't support it natively — check with:

```python
torch.cuda.is_bf16_supported()
```

## 5. Activation Checkpointing (Checkpoint Wrapper)

### What it is

Activation checkpointing (a.k.a. gradient checkpointing) is a memory-saving technique that trades **compute for memory**. In PyTorch, it's commonly applied via:

```python
from torch.utils.checkpoint import checkpoint
from torch.distributed.algorithms._checkpoint.checkpoint_wrapper import checkpoint_wrapper
```

### The problem it solves

During a normal forward pass, every intermediate activation (attention scores, softmax outputs, MLP hidden states, etc.) is kept in memory until backpropagation consumes it. For a transformer block, this includes tensors like:

- `Q`, `K`, `V` projections
- attention `scores` and `attn_weights` (shape `[batch, heads, seq_len, seq_len]` — scales quadratically with sequence length)
- the expanded MLP hidden state (`4 × hidden_dim`) before and after the activation function

Across dozens of layers, this adds up to gigabytes of activations that are only needed briefly during backward.

### How it works

Instead of retaining all intermediate activations, checkpointing:

1. **Discards** the internal activations of a wrapped block right after its forward pass.
2. **Keeps only the block's input** in memory.
3. During backward, when gradients for that block are needed, it **recomputes the forward pass** of that block from the saved input, regenerating the intermediate activations temporarily.
4. Uses those recomputed activations to calculate gradients normally, then discards them again.

```python
# Without checkpoint: all internal activations of every layer stay in memory
for layer in model.layers:
    x = layer(x)

# With checkpoint: only block inputs are kept; internals are recomputed in backward
for layer in model.layers:
    x = checkpoint(layer, x, use_reentrant=False)
```

### Mechanics under the hood

PyTorch implements this via a custom `autograd.Function`:

- **Forward**: runs inside `torch.no_grad()` (no autograd graph is built for internal ops), saves only the block's input tensor (`ctx.save_for_backward`), and also saves the RNG state (crucial if the block uses dropout).
- **Backward**: restores the saved RNG state (so recomputed dropout masks match the original), re-runs the forward pass with gradients enabled (rebuilding the local subgraph), computes gradients through it, then discards the subgraph again.

Saving/restoring RNG state matters because without it, a recomputed dropout mask would differ from the one used originally, making the gradient calculation mathematically inconsistent with the forward pass that actually produced the output.

### Trade-off

| | Without checkpoint | With checkpoint |
|---|---|---|
| Memory | High — all intermediate activations retained | Low — only block inputs retained |
| Compute | Normal | +1 extra forward pass per checkpointed block during backward (~20–30% slower training) |

### Interaction with FSDP

When combined with **Fully Sharded Data Parallel (FSDP)**, ordering matters:

```python
model = FSDP(model, auto_wrap_policy=my_policy)          # 1. shard first
apply_activation_checkpointing(model, check_fn=...)        # 2. checkpoint on top
```

FSDP wraps modules with hooks that all-gather sharded parameters into their full form before the forward pass, then re-shard them afterward. If checkpointing were applied *inside* FSDP (checkpoint wraps the raw module, FSDP wraps the checkpoint), the recomputation triggered during backward would call the raw forward function directly — bypassing the all-gather hooks — and the block would recompute with incomplete (sharded) weights, causing shape mismatches or incorrect results.

By wrapping FSDP first and checkpoint on top, the recomputation calls the *full FSDP forward* (hooks included), correctly re-gathering full weights before recomputing activations.

**Conceptual parallel**: both FSDP and activation checkpointing follow the same pattern — "keep a compact version in memory, materialize the full version on demand, use it, discard it again" — but they trade memory for different resources: FSDP trades memory for **network communication** (all-gather across GPUs), while checkpointing trades memory for **local computation** (recomputing the forward pass).

## 6. Parameter Memory Footprint

VRAM cost for a model with **N** parameters:

| Configuration | Memory |
|---|---|
| FP32 | `N × 4` bytes |
| BF16 / FP16 | `N × 2` bytes |
| Mixed precision training | `N × 8` bytes total (`4` bytes master copy + `2` bytes working copy + `2` bytes gradients) |

This is a baseline for weights, gradients, and master copies only — it does **not** include optimizer states (e.g. Adam's first/second moments add roughly `N × 8` more bytes) or activation memory, which is precisely the cost that activation checkpointing targets (see Section 5).

### Putting it together

A full training memory budget typically breaks down into:

```
Total VRAM ≈ Parameters + Gradients + Optimizer States + Activations
```

- **Parameters + Gradients + Optimizer states** → addressed by mixed precision (Section 4) and parameter sharding (FSDP)
- **Activations** → addressed by activation checkpointing (Section 5)

These techniques are complementary, not competing — modern large-scale training pipelines (Megatron-LM, DeepSpeed ZeRO, PyTorch FSDP) combine all of them simultaneously to fit models with tens or hundreds of billions of parameters into finite per-device memory.
