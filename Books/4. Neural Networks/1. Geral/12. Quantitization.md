# Quantization in Deep Learning: A Practical Guide

## 1. What Is Quantization?

Quantization is the process of representing a neural network's weights and/or activations using fewer bits than the original training precision (typically FP32 or BF16). Instead of storing a weight as a 32-bit float, you store it as an 8-bit or 4-bit integer, plus a small amount of metadata (scale, zero-point) that lets you map back to an approximate floating-point value.

In short: **fewer bits per number → smaller model, less memory bandwidth, faster math on hardware that supports low-precision ops.**

## 2. Why We Use It

| Benefit | Explanation |
|---|---|
| **Memory footprint** | INT8 uses 4x less memory than FP32; INT4 uses 8x less. A 70B parameter model at FP16 needs ~140GB; at INT4 weight-only, it can fit in ~35GB. |
| **Memory bandwidth / latency** | Most LLM inference is memory-bound, not compute-bound. Moving fewer bytes from HBM to compute units directly speeds up token generation. |
| **Throughput** | Integer matrix multiplication (INT8 GEMM) runs faster than FP16/FP32 on hardware with dedicated INT8 tensor cores (most modern GPUs, mobile NPUs, edge chips). |
| **Deployment on constrained hardware** | Mobile devices, embedded systems, and edge accelerators often only have efficient INT8/INT4 kernels, not FP32. |
| **Cost** | Smaller models mean fewer/cheaper GPUs needed to serve the same load. |

The trade-off is **accuracy degradation** — you are approximating continuous values with a discrete grid. The whole practice of quantization is about minimizing that accuracy loss while maximizing the efficiency gain.

## 3. The Core Math: Scale and Zero-Point

Quantization maps a floating-point range `[min, max]` to an integer range (e.g., `[-128, 127]` for INT8 signed, or `[0, 255]` unsigned).

### Affine (asymmetric) quantization

```
x_int = round(x_float / scale) + zero_point
x_float ≈ (x_int - zero_point) * scale
```

- **`scale`** — a floating-point number that defines the "step size" between adjacent integer values. It's computed from the observed range:
  ```
  scale = (max_float - min_float) / (max_int - min_int)
  ```
- **`zero_point`** — the integer value that represents float `0.0`. This matters because `0` needs to be exactly representable (e.g., for padding, ReLU outputs, etc.). In symmetric quantization, `zero_point = 0` by construction.

### Symmetric quantization

Simpler and more common for weights:

```
scale = max(abs(min_float), abs(max_float)) / max_int
x_int = round(x_float / scale)
x_float ≈ x_int * scale
```

No zero-point needed since the range is centered at zero. This is why most weight-only configs (e.g., `Int8WeightOnlyConfig` in torchao) default to symmetric quantization — it's cheaper to compute and works well for weight distributions, which tend to be roughly zero-centered.

### Why activations often need asymmetric quantization

Activations after a ReLU or GELU are not zero-centered — they can be strictly non-negative. Forcing symmetric quantization on such a distribution wastes half your integer range. That's why activation quantization sometimes uses `MappingType.ASYMMETRIC` and a `zero_point`, while weight quantization sticks to `SYMMETRIC`.

### What is `scale_x` (or `act_quant_scale`)?

When you see something like `act_quant_scale` or `scale_x` in library code, it refers specifically to **the scale used to quantize the activation tensor** (as opposed to `scale_w`, the weight's scale). In a quantized linear layer, you generally have two independent quantization schemes running side by side:

```
y = (x_int - zp_x) * scale_x  @  (w_int - zp_w) * scale_w
```

Since `scale_x` and `scale_w` are just numbers (or per-row/per-channel vectors), they can be factored out of the integer matmul and applied once at the end:

```
y ≈ scale_x * scale_w * (x_int @ w_int)   # + zero-point correction terms if asymmetric
```

This is *why* quantized matmuls are fast: the expensive operation (`x_int @ w_int`) happens in integer arithmetic, and the floating-point rescaling is a cheap elementwise multiply afterward.

### Granularity: per-tensor vs. per-channel vs. per-group

- **Per-tensor**: one `scale`/`zero_point` for the entire tensor. Cheapest, least accurate.
- **Per-channel (per-row)**: one scale per output channel of a weight matrix. Much better accuracy for weights, negligible overhead since weights are static.
- **Per-group**: split each channel into groups of N elements (e.g., `group_size=128`), each with its own scale. Used heavily for INT4 weight quantization, where per-channel alone isn't fine-grained enough to preserve accuracy at 4 bits.

## 4. PTQ vs. QAT

### Post-Training Quantization (PTQ)

You take an already-trained, full-precision model and quantize it **after the fact**, with no (or minimal) retraining.

- **Pros**: fast, cheap, no need for training infrastructure or labeled data at scale.
- **Cons**: accuracy loss can be significant, especially at low bit-widths (INT4 and below) or on sensitive layers.
- **Two flavors**:
  - **Dynamic PTQ**: activation ranges computed on-the-fly at inference time (see section 5).
  - **Static PTQ**: activation ranges pre-computed via a calibration pass before deployment (see section 5).

PTQ is the default choice for most LLM serving scenarios today (e.g., quantizing a Llama checkpoint for inference) because retraining a multi-billion parameter model just to quantize it is often not worth the cost.

### Quantization-Aware Training (QAT)

You simulate quantization *during* training (or fine-tuning), inserting "fake quantization" ops in the forward pass so the model learns weights that are robust to the rounding error it will experience at inference time. Gradients still flow in full precision (using a straight-through estimator to get around the fact that `round()` has zero gradient almost everywhere).

- **Pros**: recovers most of the accuracy lost to PTQ, especially critical at INT4 or below.
- **Cons**: requires a training loop, compute, and (ideally) representative training data. Much more expensive than PTQ.
- **When to use it**: aggressive quantization (INT4, INT3), quality-sensitive deployments, or when PTQ alone doesn't hit your accuracy bar.

torchao reports QAT recovering the large majority of the accuracy drop seen with plain PTQ on INT4 Llama models — this is the general pattern: QAT closes most of the gap PTQ leaves behind, at the cost of a training run.

**Rule of thumb:**
```
INT8 weight-only          → PTQ is usually fine
INT8 dynamic activation   → PTQ is usually fine
INT4 weight-only          → PTQ works, but QAT helps meaningfully
INT4 + activation quant   → QAT strongly recommended
```

## 5. Dynamic vs. Static Quantization

Both are PTQ techniques; the difference is **when and how the activation scale is determined.**

### Dynamic Quantization

The scale (and zero-point, if asymmetric) for activations is computed **at runtime, per forward pass** — typically per-token or per-batch, by looking at the actual min/max of the incoming activation tensor.

```
# conceptually, happens inside every forward pass:
scale_x = compute_from(x.min(), x.max())
x_int = quantize(x, scale_x)
y = matmul(x_int, w_int) * scale_x * scale_w
```

- **No calibration step needed.** Just wrap the model and run.
- Adapts naturally to distribution shift between calibration data and real traffic, since there is no calibration data.
- Small runtime overhead: computing min/max and the scale on every forward pass.
- This is what `Int8DynamicActivationInt8WeightConfig` (torchao) or standard "dynamic quantization" in PyTorch (`torch.quantization.quantize_dynamic`) does.

### Static Quantization

The activation scale is **fixed ahead of time**, computed once during a calibration phase where you run representative sample data through the model with observers attached, recording the distribution of activations layer by layer.

```
# calibration phase (offline, once):
for batch in calibration_dataset:
    observer(model(batch))   # observer records min/max per layer
scale_x = observer.calculate_qparams()

# inference phase (repeated, no recomputation):
x_int = quantize(x, scale_x)   # scale_x is now a constant
y = matmul(x_int, w_int) * scale_x * scale_w
```

- **Requires a calibration dataset** that's representative of production traffic.
- **Zero runtime overhead** for computing scales — they're baked in.
- **Accuracy risk**: if production data distribution drifts from the calibration set, the fixed range may clip or under-utilize the quantization grid, silently hurting accuracy.
- Best suited for latency-critical serving where the extra runtime cost of dynamic scale computation is unacceptable, and where input distributions are stable and well understood (e.g., fixed-domain vision models, well-characterized production traffic).

### Side-by-side comparison

| | Dynamic | Static |
|---|---|---|
| Calibration dataset required | No | Yes |
| Setup complexity | Low | Higher (observers, calibration run, qparam extraction) |
| Runtime overhead | Small (recomputes scale every forward) | None (scale baked in) |
| Robustness to distribution shift | High | Lower — fixed range can go stale |
| Typical use case | LLM inference, general-purpose serving | Latency-critical, stable-input production pipelines |
| Common library example | `Int8DynamicActivationInt8WeightConfig` | `Int8StaticActivationInt8WeightConfig` |

**Weight-only quantization** (e.g., `Int8WeightOnlyConfig`, common for LLMs) doesn't fall into either bucket in the same way — weights are static by definition, so their scale is always computed once, ahead of time, directly from the trained weight tensor. The dynamic-vs-static distinction really only matters for **activations**.

## 6. Practical Decision Guide

```
Start here
│
├── Need max simplicity, "just quantize it"? → PTQ, weight-only INT8 or INT4
│
├── Serving an LLM, need decent speedup, no time for calibration/training?
│     → PTQ, dynamic activation quantization (INT8 dynamic act + INT8/INT4 weight)
│
├── Need max throughput, input distribution is stable and known?
│     → PTQ, static activation quantization (requires calibration set)
│
└── Accuracy is degrading too much at INT4 (or below)?
      → QAT (fine-tune with fake-quant ops, then convert)
```
