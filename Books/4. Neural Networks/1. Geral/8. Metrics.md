# Metrics

Metrics measure what you actually care about. Loss is what the model optimizes — metrics are how you evaluate if that optimization is working.

In regression, loss and metric often coincide (MSE is differentiable, so it serves as both). In classification they diverge — cross-entropy is the loss, but accuracy/F1/AUC are the metrics that matter.

---

## Regression

| Metric | Formula | Notes |
|---|---|---|
| MSE | `Σ(y - ŷ)² / n` | Penalizes large errors heavily |
| RMSE | `√MSE` | Same unit as target, easier to interpret |
| MAE | `Σ|y - ŷ| / n` | Robust to outliers |
| R² | `1 - SS_res/SS_tot` | Proportion of variance explained. 1 is perfect |

MSE and MAE are differentiable — used as loss and metric at the same time.

---

## Classification

None of these are differentiable — cross-entropy is the loss, these are evaluation only.

### Accuracy

```
(TP + TN) / (TP + TN + FP + FN)
```

Of everything predicted, how much was correct. Useless on imbalanced data — a model that always predicts the majority class gets 95% accuracy on a 95/5 dataset and is completely useless.

### Precision

```
TP / (TP + FP)
```

Of everything predicted as positive, how much was actually positive. Use when **false positives are costly** — spam filter wrongly blocking a legitimate email, ad system charging for fake clicks.

High precision = when the model says "yes", it's usually right.

### Recall

```
TP / (TP + FN)
```

Of all real positives, how many did the model catch. Use when **false negatives are costly** — cancer detection missing a real tumor, fraud detection missing a real transaction.

High recall = the model misses few real positives.

### Precision vs Recall tradeoff

They oppose each other. Lowering the classification threshold catches more positives (recall ↑) but also more false alarms (precision ↓). You tune the threshold based on what's more costly in your context.

### F1

```
2 * (Precision * Recall) / (Precision + Recall)
```

Harmonic mean of precision and recall. Use on imbalanced classes when you want to balance both. A model that always predicts positive gets recall=1 but precision≈0, so F1≈0 — it exposes useless models that accuracy hides.

### Summary

| Metric | Formula | Use when |
|---|---|---|
| Accuracy | `(TP+TN) / all` | Balanced classes |
| Precision | `TP / (TP+FP)` | FP is costly (spam, ads) |
| Recall | `TP / (TP+FN)` | FN is costly (cancer, fraud) |
| F1 | `2*P*R / (P+R)` | Imbalanced, want both |
| AUC-ROC | area under curve | Threshold-independent ranking |

```python
from torchmetrics import Accuracy, F1Score, Precision, Recall, AUROC

acc  = Accuracy(task='multiclass', num_classes=10).to(device)
f1   = F1Score(task='multiclass', num_classes=10, average='macro').to(device)
prec = Precision(task='multiclass', num_classes=10, average='macro').to(device)
rec  = Recall(task='multiclass', num_classes=10, average='macro').to(device)
```

## Language Models

| Metric | Notes |
|---|---|
| Perplexity | `exp(cross-entropy)`. Standard for comparing LLMs during pretraining |
| BLEU | N-gram overlap. Used in translation |
| ROUGE | Recall-based n-gram overlap. Used in summarization |
| Exact Match | Token-level match. Used in QA (SQuAD) |

Perplexity in PyTorch:

```python
loss = criterion(output, target)  # cross-entropy
perplexity = torch.exp(loss)
```

In practice, LLM evaluation goes beyond single metrics — benchmarks like MMLU, HumanEval, and HellaSwag are task suites that measure reasoning, coding, and commonsense.

## In PyTorch

TorchMetrics handles batch accumulation and multi-GPU correctly:

```python
from torchmetrics import Accuracy

acc = Accuracy(task='multiclass', num_classes=10).to(device)

for batch in dataloader:
    preds = model(x)
    acc.update(preds, y)      # accumulates across batches

final = acc.compute()         # computes over full dataset
acc.reset()                   # clear state for next epoch
```

sklearn works but requires moving tensors off GPU:

```python
from sklearn.metrics import f1_score

preds = model(x).argmax(dim=1).cpu().numpy()
f1_score(y.cpu().numpy(), preds, average='macro')
```

Use TorchMetrics in the training loop, sklearn for offline analysis and reports.

## Train vs Val metrics

Always track metrics on both splits:

```
train loss ↓  val loss ↓  → learning
train loss ↓  val loss ↑  → overfitting
train loss ↑  val loss ↑  → underfitting
```

A low loss doesn't guarantee good metrics — especially with imbalanced data or when the loss is a proxy for the real metric (cross-entropy → F1).

## Confusion Matrix

Rows = what it **was** (real), Columns = what the model **predicted**:

```
                 Predicted Positive (PP)   Predicted Negative (PN)
Real Positive (RP)        TP                        FN
Real Negative (RN)        FP                        TN
```

How to read:
- **T/F** — whether the model was right or wrong
- **P/N** — what the model predicted

So:
- `TP` — predicted positive, was positive → correct
- `TN` — predicted negative, was negative → correct
- `FP` — predicted positive, was negative → false alarm
- `FN` — predicted negative, was positive → missed it

Cancer detection example:

```
model predicted: no cancer (negative)
real label: has cancer (positive)
→ FN — the worst kind of error in this context
```

```python
from sklearn.metrics import confusion_matrix

cm = confusion_matrix(y_true, y_pred)
# cm[0][0] = TP   cm[0][1] = FN
# cm[1][0] = FP   cm[1][1] = TN
```
