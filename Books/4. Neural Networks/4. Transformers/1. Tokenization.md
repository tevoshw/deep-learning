# Tokenization Explained

# 1. What Are Tokens?

A **token** is the atomic unit of text that a language model actually processes. Neural networks work with numbers, not raw strings — so before any text reaches a model, it must be converted into a sequence of integers (token IDs). Each ID maps to a row in the model's embedding matrix, which is where the model's "understanding" of that unit lives.

A token can represent:
- A whole word (`"the"`)
- Part of a word (`"tion"`, `"un"`)
- A single character
- A single byte
- Whitespace, punctuation, or a special control marker

The **tokenizer** is the component responsible for this text ↔ token ID conversion, in both directions (encoding and decoding).

---

# 2. Why Tokenization Exists

Models can't read text directly, so you need a mapping between language and numbers. The challenge is choosing the right **granularity** for that mapping — too coarse (whole words) and you get a massive, brittle vocabulary; too fine (individual characters) and sequences become extremely long and inefficient. This tradeoff is exactly what the four tokenization types below address.

---

# 3. Types of Tokenization

### 3.1 Character-level

Every single character becomes one token.

```
"lower" → ["l", "o", "w", "e", "r"]
```

**Pros:**
- Tiny, fixed vocabulary (just the alphabet + symbols)
- No out-of-vocabulary (OOV) problem — any text can be represented

**Cons:**
- Sequences become very long (5 tokens for a 5-letter word)
- The model has to learn spelling and word structure from scratch, wasting capacity
- Loses semantic structure — no direct notion of "words"

---

### 3.2 Word-level

Each whole word is one token.

```
"the lower price" → ["the", "lower", "price"]
```

**Pros:**
- Short, semantically meaningful sequences
- Intuitive mapping to linguistic units

**Cons:**
- Vocabulary explodes (hundreds of thousands of words across a language, more with morphology-heavy languages)
- Severe **out-of-vocabulary problem**: any word not seen during training (typos, new slang, rare names) breaks the system or falls back to an `<unk>` token, losing information
- Doesn't share structure between related words (`"lower"`, `"lowest"`, `"lowering"` are all treated as unrelated)

---

### 3.3 Subword-level (the modern standard)

A middle ground: frequent words become a single token, rare or complex words are broken into meaningful chunks.

```
"lower" → ["low", "er"]
"unhappiness" → ["un", "happi", "ness"]
```

**Pros:**
- Manageable vocabulary size (typically 30k–150k tokens)
- No true OOV problem — rare words degrade gracefully into smaller known pieces instead of breaking
- Captures some morphological structure (prefixes, suffixes, roots)

**Cons:**
- Word boundaries aren't always intuitive to humans
- Different languages tokenize with different efficiency depending on what the training corpus contained

This is what almost all modern LLMs use, generated via algorithms like **BPE**, **WordPiece**, or **Unigram LM**.


### Quick Comparison

| Type | Vocab size | Sequence length | OOV problem | Used by |
|---|---|---|---|---|
| Character | Very small | Very long | None | Rarely used alone today |
| Word | Very large | Short | Severe | Older NLP systems (pre-2018) |
| Subword | Medium (30k–150k) | Medium | Minimal | BERT (WordPiece), T5/Llama (Unigram/SentencePiece) |

# 4. Special Tokens

Beyond tokens that represent actual text content, tokenizers reserve a set of **special tokens** — symbolic markers that carry structural or control information rather than language content. They're added to the vocabulary but don't come from the BPE/merge process itself.

Common special tokens include:

| Token | Purpose |
|---|---|
| `<bos>` / `<s>` | Beginning of sequence |
| `<eos>` / `</s>` | End of sequence — signals the model to stop generating |
| `<pad>` | Padding — fills shorter sequences in a batch to match the longest one |
| `<unk>` | Unknown token — represents input the tokenizer couldn't map (rare with byte-level tokenizers, since they can always fall back to raw bytes) |
| `<mask>` | Used in masked language modeling (e.g., BERT pretraining) to hide a token the model must predict |
| `<sep>` | Separator between two distinct segments of input (e.g., question vs. context) |
| Chat/role tokens | Modern chat models add tokens like `<|user|>`, `<|assistant|>`, `<|system|>` to mark conversation structure |

Special tokens are inserted **around or between** the regular tokens produced by the tokenizer, right before the sequence is fed into the model:

```
Raw text → tokenized → [<bos>, 15234, 8821, 9042, <eos>]
```

They're essential for the model to understand structure — where a prompt starts and ends, where padding should be ignored, or where one speaker's turn ends and another's begins.

> Special tokens will not be fixed, more and more have always appeared, not limited to one number, each occasion can have one in its context, so decorating does not solve, but rather understand how they work and their functions

---

## The Full Pipeline (Recap)

```
1. Raw text
2. Encode to bytes (UTF-8)
3. Pre-tokenization (split into candidate chunks — words/punctuation via regex)
4. Apply learned BPE merges (within each chunk)
5. Resulting token IDs
6. Add special tokens (<bos>, <eos>, etc.)
7. Feed into the model's embedding layer
```

Decoding reverses this: token IDs → bytes → UTF-8 decode → readable text.
