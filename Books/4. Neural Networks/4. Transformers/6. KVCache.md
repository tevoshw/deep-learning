## What is it?

KV Cache (Key-Value Cache) is an optimization technique used during **autoregressive inference** in transformer models. It avoids recomputing the Key (K) and Value (V) projections for every previously generated token at each new generation step, dramatically speeding up text generation.

## The problem it solves

In a transformer's self-attention layer, every token attends to all previous tokens. Attention is computed as:

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

During **autoregressive generation** (predicting one token at a time, like GPT-style models), without caching:

- To generate token $t$, the model needs $K$ and $V$ for all tokens $1$ to $t$
- To generate token $t+1$, it needs $K$ and $V$ for all tokens $1$ to $t+1$
- Naively, this means **recomputing $K$ and $V$ for every previous token, at every single generation step** — even though those tokens never change

This makes generation cost grow **quadratically** with sequence length: $O(n^2)$ total compute for generating $n$ tokens.

## How KV Cache fixes this

Key insight: once a token's Key and Value vectors are computed, **they never change** in subsequent steps (because of causal masking — a token only ever attends to itself and earlier tokens, never later ones).

So instead of recomputing them:

1. **Compute once**: when a token is processed for the first time, compute its $K$ and $V$ vectors and store them in a cache (per layer, per attention head)
2. **Reuse on every future step**: for each new token generated, only compute $Q$, $K$, $V$ for that **single new token**
3. **Concatenate**: append the new $K$ and $V$ to the cached ones, and compute attention using the full cached sequence

This reduces the per-step cost from $O(t)$ (recomputing everything) to $O(1)$ new computation plus a lookup — turning the total generation cost from $O(n^2)$ into $O(n)$.

## What actually gets cached

For each transformer layer, and for each attention head:

- **Key cache**: tensor of shape `[batch_size, num_heads, sequence_length, head_dim]`
- **Value cache**: same shape

Only $K$ and $V$ are cached — **not** $Q$, because $Q$ is only needed for the current token being generated; it's never reused for future steps.

## Memory cost

KV Cache trades **compute for memory**. Memory usage scales with:

$$\text{Cache size} \propto \text{num\_layers} \times \text{num\_heads} \times \text{head\_dim} \times \text{sequence\_length} \times \text{batch\_size} \times 2 \text{ (K and V)}$$

For large models with long context windows, this can become the dominant memory bottleneck during inference — often larger than the model weights themselves at long sequence lengths.

## Techniques to reduce KV Cache memory

Because the cache can become huge, several optimizations exist:

- **Multi-Query Attention (MQA)**: all attention heads share a single Key and Value projection (only Query stays per-head), drastically cutting cache size
- **Grouped-Query Attention (GQA)**: a middle ground — groups of heads share K/V projections instead of a single shared one, balancing quality and memory savings
- **Quantized KV Cache**: storing cached K/V in lower precision (e.g. int8, fp8) instead of fp16/fp32
- **PagedAttention** (used in vLLM): manages KV cache memory in non-contiguous blocks (like OS virtual memory paging), reducing fragmentation and enabling more efficient batching
- **Sliding window attention**: only caches the most recent $w$ tokens, discarding older ones, bounding memory regardless of sequence length

## Why this matters in practice

- It's the reason inference frameworks like vLLM, TensorRT-LLM, and Hugging Face `transformers` all implement KV caching by default for generation
- It's central to why **prefill** (processing the initial prompt) and **decode** (generating new tokens one at a time) are treated as distinct phases with very different compute characteristics — prefill is compute-bound, decode is memory-bandwidth-bound (dominated by reading the KV cache)
- Understanding KV cache is essential for reasoning about serving costs, batching strategies, and context length limits in production LLM systems
